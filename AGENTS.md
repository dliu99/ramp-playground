# PR Understanding Quiz Hook

## Project purpose

This project explores a local learning checkpoint for pull-request authors. The long-term goal is to help developers understand the code they are about to push, especially when some or all of it was generated by an agent.

The experience should eventually examine the pushed diff, decide whether the change merits a quiz, and ask questions that encourage active recall and a correct mental model of the change. The checkpoint is meant to teach, not merely add friction or create a compliance checkbox.

This repository is currently at the infrastructure stage. It contains only the local Git hook, Git-context collection, and a minimal confirmation CLI. Do not mistake the current confirmation prompt for the final product.

## Product direction

The intended user is the author pushing a branch that will become a pull request. The primary interaction remains local and happens before code leaves the machine.

Future versions may include:

- An LLM decision about whether a pushed change is substantial enough to quiz.
- Structured questions grounded in exact files, hunks, control flow, and behavioral changes.
- Hints, explanations, and a way to ask follow-up questions when the author is stuck.
- A teach-back step in which the author explains the change in their own words.
- Reuse of that teach-back as the basis of a pull-request description.
- A richer terminal experience or an optional local web renderer driven by validated JSON.

These are product goals, not authorization to implement them preemptively. Keep the current milestone small until the user requests the next layer.

## Current behavior

The repository uses Bun and TypeScript. A tracked `pre-push` hook invokes the CLI with the ref updates Git provides on stdin.

For each pushed, non-deleted ref, the CLI displays:

- The local and remote ref names.
- The local and remote commit SHAs.
- The number of commits when a comparison range can be determined.
- A changed-file count and short diff statistic when available.

The CLI then asks whether the push should continue. Approval returns exit code `0`; rejection returns a nonzero exit code and stops the push. Deletion-only pushes continue without confirmation.

Git uses stdin to deliver pre-push ref updates, so interactive confirmation must use the controlling terminal at `/dev/tty`. Do not change the prompt to read from process stdin after the ref input has been consumed.

When no controlling terminal exists, input is malformed, or Git cannot provide optional summary information, the tool must not strand the developer. Operational failures fail open with a clear warning. An explicit user rejection still fails closed. `PR_QUIZ_BYPASS=1` is the intentional escape hatch because local Git hooks can never provide hard enforcement.

## Architecture

- `.githooks/pre-push` is deliberately tiny. It forwards Git's arguments and stdin to the Bun CLI and preserves the CLI exit code.
- `src/cli.ts` coordinates parsing, display, Git summaries, and confirmation. It owns the executable adapter that separates Git stdin from `/dev/tty`.
- `src/refs.ts` owns typed pre-push ref parsing, deletion detection, and ref/SHA presentation.
- `src/git.ts` owns read-only Git inspection and construction of push summaries.
- `src/confirmation.ts` defines the interaction boundary that a future quiz runner can extend or replace.
- `src/hooks.ts` owns repository-local hook installation and removal through `core.hooksPath`.

Preserve these boundaries. Git plumbing should not depend on rendering, and future learning logic should not be embedded in the shell hook. Keep the hook easy to inspect and make richer behavior live behind typed TypeScript interfaces.

## Git range semantics

For an existing remote branch, compare the remote SHA supplied by Git with the local SHA being pushed. For a new branch whose remote SHA is all zeroes, attempt to use the merge base with `origin/main`. If a useful base cannot be found, show the ref information and omit optional summary fields instead of blocking the push.

Deleted refs have an all-zero local SHA or the special `(delete)` local ref. They should not enter the learning flow.

Multiple ref updates may arrive in one hook invocation. Render every update, but ask for confirmation once for the overall push.

## Durable constraints

- Use Bun as the runtime and package manager.
- Keep the tool local-first and author-focused.
- Do not introduce a hosted service, GitHub check, merge gate, database, telemetry, or account system without an explicit product decision.
- Do not send repository contents to a model until model integration and privacy behavior are explicitly requested.
- Do not execute model-authored code or arbitrary model-authored HTML. A future generative UI must use a small validated component schema.
- Do not silently block pushes because infrastructure is unavailable.
- Do not remove the explicit bypass; local hooks are advisory by design.
- Do not create tests under the standing instruction at the top of this file.

## Current non-goals

There are currently no model calls, quiz generation, scoring, risk classification, games, web UI, persisted quiz receipts, tutor conversations, or PR-description generation. Avoid adding placeholder frameworks for these features. Add each capability only when its product behavior is ready to be decided.

When extending the project, prefer the smallest vertical addition that teaches us something about the author experience while keeping the hook reliable and easy to remove.
